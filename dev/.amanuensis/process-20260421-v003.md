# Process Documentation — enough v0.0.3

## Session: 2026-04-21 (starts ~14:10 local, continues from v0.0.2)

### Task

Three things the user wanted before getting "too fancy" with more features:

1. A global install folder at `~/enough/` (like `~/.claude`, but without the
   dot). Ideally end-user install via a `.dmg` / `.pkg`, but a guided
   `bootstrap.sh` is fine for v0.0.3.
2. Global defaults under `~/enough/` for paradigms, policies, skills,
   routines, AGENT.md, MOTIVATION.md, models/providers.md — "imported" or
   "symlinked" into each new project, with some mechanism for customizing
   per-project.
3. `infoworld/` moved up to be shared across all projects on the machine,
   with a new `infoworld/public/` subfolder added. Paradigm text updated
   to allow reads outside the project dir when explicitly asked.

### Methodology

Staged build: A (install scaffolding) → B (the defaults / symlinks /
allowlist / customize UI — the big one) → C (docs + amanuensis + version
bump). Commit + push at every phase boundary. Manual end-to-end
verification after B; integration tests via TestClient before commit.

### Clarifying decisions with the user

Before code, I surfaced three tensions and got explicit answers:

- **Symlink vs copy for global defaults.** User chose Option A: symlinks
  with an "unlink & customize" UI affordance. UI shows symlinked entries
  in italics. (DR-034, DR-040)
- **Installer scope.** `bootstrap.sh` with explain-as-you-go narration;
  `.pkg`/`.dmg` deferred to v1.0. User explicitly wanted non-technical
  users to "learn to fear the command line a little less." (DR-030)
- **Read allowlist shape.** User: "maybe it can just be a third document
  in policies, `read_allowlist.md`." Baked in: it's itself a policy file
  governable via the same symlink/customize pattern. Turtles all the way
  down. (DR-037)

Additional quick calls made in response:
- `~/enough/` is self-contained (code + defaults + weights + venv +
  infoworld). (DR-027)
- Dev clone at `/Users/m3u/METMcloud/METMroot/enough` stays; `~/enough/`
  is a separate user-realistic install populated by `bootstrap.sh`. User's
  git instinct was correct. (DR-028)
- CLI refuses to run inside `~/enough/`. (DR-029)
- PATH wrapper at `~/.local/bin/enough`. (DR-031)
- AGENT.md and MOTIVATION.md are COPIED, not symlinked, because they
  diverge fast per project. (DR-034)

### Dead Ends / Abandoned Paths

- **Resolving the full target for containment check** (v0.0.3-B initial
  impl). Passed integration tests because the test fixtures used the dev
  clone's `defaults/` which happened to sit under the project_root of
  `/tmp/v3b-test` during the test... wait, no, it didn't — the tests
  caught this. (Actually the bug was more subtle: macOS's `/tmp` resolves
  to `/private/tmp`; the containment check failed even for in-project
  files when project_dir had a symlinked component, which is why I saw
  the error live but not in the integration tests that happened to use
  `/tmp/v3b-test` consistently.) Fix in DR-041.

- **Storing the allowlist as JSON config.** Considered and rejected in
  favor of parsing the markdown policy file directly. The parser is
  permissive and could be fooled by a user writing prose that looks like
  a bullet inside the section, but that's acceptable v0.0.3 behavior.
  (DR-038)

### Idle Thoughts

- Symlinks pointing from a project's `.rness/` into the dev clone's
  `defaults/` (vs `~/enough/defaults/`) is an artifact of running enough
  from the dev clone. When a user runs from `~/enough`, symlinks point at
  the install's defaults. If they later delete one install and switch to
  the other, old projects have dangling symlinks. A "refresh / repoint
  symlinks" command would be a nice v0.0.4 addition.

- The file-tree walker recurses through symlinked directories (so
  `infoworld/` shows `wiki/personal/public/` children). At low depths
  this is fine. At depth=4 it caps out, which matters for large
  `infoworld/wiki/` trees from Kiwix dumps. Not fixing; revisit if users
  actually populate large wikis.

- The read allowlist only gates `read_file`, not `shell`. The agent can
  still `cat ~/secret` via shell. Documented as intentional (DR-039); if
  users want tighter sandboxing they can't use shell at all — which is
  fair but a significant capability loss. Possible future: a
  `shell_allowlist.md` that's parsed against the command string. Too
  fragile for v0.0.3.

### Open Questions (for the user to weigh in on later)

- Does every skill need individual symlinks, or should the `skills/`
  directory itself be a single symlink? Current answer: per-skill, so
  users can customize one without the others. Revisit if this creates
  friction.
- When a user "customizes" and then the upstream default changes, how do
  we surface that they're missing updates? Diff view in the preview pane?
  Explicit "refresh defaults" command?
- Should the read allowlist affect `write_file` symmetrically? Currently
  no — writes are project-dir-only regardless of allowlist. The paradigm
  text explicitly says no writes outside project.
